\section{Introducción y objetivo}
Se investigó el uso de MLflow en la plataforma Databricks y se adaptó el pipeline de scikit-learn del proyecto Champions League, desarrollado en el Taller 3 y la Actividad 9 [6]. El objetivo fue centralizar el seguimiento de entrenamiento, conservar modelos reutilizables y comprobar la misma lógica desde un Jupyter Notebook y un archivo Python.

La implementación se ejecutó en Databricks Free Edition con compute Serverless. Ambos formatos completaron la búsqueda de hiperparámetros de SVC, guardaron el modelo y verificaron su recarga. Este reporte presenta los resultados de esas ejecuciones, realizadas el 16 de octubre de 2026, hora de Guatemala.

\subsection{MLflow y su integración con Databricks}
MLflow organiza ejecuciones y empaqueta modelos. Databricks ofrece un servicio administrado de seguimiento y herramientas integradas para continuar su ciclo de vida [1]. En esta implementación, \texttt{uri="databricks"} dirige los registros al workspace y una ruta absoluta identifica el experimento [2].

Las funcionalidades aplicadas son: \textbf{Experiments}, para agrupar ejecuciones; \textbf{Tracking}, para conservar parámetros, métricas y artefactos; \textbf{Dataset Tracking}, para relacionar los datos con cada run; y \textbf{MLflow Models}, para guardar y cargar el pipeline completo [2, 5]. Model Registry en Unity Catalog, Feature Store y Model Serving forman parte del ecosistema, con configuración y objetivos específicos [1, 3, 4].

\subsection{¿Qué usos puede tener en proyectos de Machine Learning?}
\begin{itemize}
\item Comparar configuraciones y modelos mediante métricas registradas.
\item Mantener trazabilidad de los datos y parámetros usados en cada entrenamiento.
\item Compartir resultados del equipo sin depender de salidas aisladas de notebooks.
\item Recuperar el pipeline con sus transformaciones y firma para realizar inferencia.
\item Preparar procesos de versionado y operación con servicios adicionales de la plataforma.
\end{itemize}

En Champions League, estas capacidades permiten evaluar variantes del clasificador y conservar evidencia de la configuración elegida. Las variables incluyen estadísticas del encuentro: el ejercicio clasifica resultados con datos observados durante el partido y no demuestra capacidad de pronóstico previo.

\section{Implementación del pipeline}
\subsection{Datos y preprocesamiento}
El CSV contiene 151 filas iniciales. Tras retirar separadores vacíos quedan 144 partidos válidos. Se utilizaron 115 observaciones para entrenamiento y 29 para prueba, con partición estratificada y semilla 42. La variable objetivo representa victoria local, victoria visitante o empate.

Se excluyeron \texttt{score} y \texttt{winner} para evitar que la respuesta forme parte de las entradas. \texttt{ColumnTransformer} procesa grupos numéricos, porcentajes como texto, razones y equipos; aplica conversiones, imputación, escalado y One-Hot Encoding. El pipeline incorpora \texttt{SelectKBest} y el clasificador. El preprocesamiento se ajusta dentro de cada fold de la búsqueda.

\subsection{Entrenamiento y configuración}
Se reutilizó \texttt{entrenar\_familia} del módulo de seguimiento del Taller 3. Se optimizó F1 macro mediante RandomizedSearchCV, con 40 configuraciones y cinco particiones de validación estratificada. La búsqueda se realiza sobre entrenamiento; el conjunto de prueba se conserva para evaluación.

\begin{lstlisting}[language=Python]
URI = "databricks"
EXPERIMENTO = (
    "/Users/fue22944@uvg.edu.gt/"
    "Champions_Resultado_Databricks"
)
FAMILIA = "svc"
N_ITER = 40
FOLDS = 5
MODELO_UC = None
\end{lstlisting}

\subsection{Notebook y archivo Python}
El notebook importa \texttt{ejecutar} del archivo Python de la raiz. Para resolver los módulos propios se incorporaron a \texttt{sys.path} la raiz del repositorio y su carpeta \texttt{src}. Se instaló el proyecto en el entorno del notebook y se reinició Python antes de importar las bibliotecas.

El notebook ejecutó la función con \texttt{formato="notebook"}. Posteriormente se probó el archivo \texttt{.py} mediante \texttt{runpy.run\_path(..., run\_name="\_\_main\_\_")} y argumentos de línea de comandos, dentro del mismo entorno de Databricks. Esta segunda ejecución valida el punto de entrada del script; no corresponde a un Job independiente.

\subsection{Hiperparámetros seleccionados}
\begin{itemize}
\item \texttt{C = 0.17535949529764422}.
\item \texttt{class\_weight = balanced} y \texttt{kernel = linear}.

\subsection{Interpretación}
La exactitud de prueba de 65.52\% corresponde a 19 aciertos entre 29 partidos. El F1 macro de 0.601010 supera la referencia de clase mayoritaria de 0.217054. La igualdad entre ambos formatos muestra consistencia de la ejecución bajo la configuración utilizada; la recarga reprodujo el F1 macro de prueba.

La prueba inicial de dos iteraciones y tres folds obtuvo F1 macro de prueba de 0.646825. Esa cifra aislada no se utiliza para seleccionar el modelo: la búsqueda completa selecciona hiperparámetros por validación cruzada, y su esquema de validación es distinto. El conjunto de prueba pequeño limita la generalización de cualquier cifra individual.

Las cifras completas coinciden con la SVC reportada en el Taller 3. Las demás familias del taller son antecedentes y no se presentan como nuevas ejecuciones de esta entrega.

\subsection{Estado del modelo}
Ambos modelos quedaron guardados con una URI de MLflow Models y su recarga fue verificada. El valor \texttt{version=null} indica ausencia de una versión registrada en Model Registry; no significa que haya fallado el guardado. Se mantuvo \texttt{MODELO\_UC=None}, sin registrar versiones ni alias en Unity Catalog y sin publicar Model Serving.

\section{Conclusiones}
Se ejecutó la integración de scikit-learn y MLflow en Databricks tanto desde un notebook como desde un archivo Python. Ambos formatos obtuvieron el mismo F1 macro de validación de 0.637570 y F1 macro de prueba de 0.601010, con recarga verificada del modelo.

MLflow permitió vincular las ejecuciones con sus parámetros, métricas y modelos. La implementación conserva las transformaciones del pipeline y utiliza validación cruzada para seleccionar hiperparámetros, proporcionando trazabilidad y una forma consistente de recuperar el modelo.

Dentro de CRISP-DM, el aporte más directo se encuentra en modelado y evaluación. Databricks amplía el soporte a preparación, colaboración y operación mediante servicios complementarios. El alcance demostrado en este laboratorio es Experiments, Tracking, Dataset Tracking y Models.
